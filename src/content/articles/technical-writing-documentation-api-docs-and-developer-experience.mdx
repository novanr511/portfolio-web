Good documentation is the difference between adoption and abandonment.

**Direct answer:** Technical writing creates documentation that helps users and developers understand, adopt, and troubleshoot products. Types: conceptual (guides, tutorials), reference (API, CLI), task-based (how-to), troubleshooting. Docs-as-code treats documentation like software: version control, CI/CD, review, testing, automation. Developer Experience (DX) measures how easily developers succeed with your product.

## Documentation types

**Getting started / Quickstart:** 5-min path to first success. Prerequisites, install, hello world, next steps.

**Guides / Tutorials:** task-oriented, step-by-step, learning goal. "How to build X."

**Conceptual / Explanatory:** why, not how. Architecture, concepts, design decisions, trade-offs.

**Reference / API docs:** exhaustive, machine-readable (OpenAPI/Swagger), auto-generated from code. Endpoints, parameters, responses, errors, examples.

**How-to / Task-based:** solve specific problem. "How to configure X." Prerequisites, steps, verification, troubleshooting.

**Troubleshooting / FAQ:** symptoms, causes, solutions. Searchable, structured.

**Changelog / Release notes:** version, date, added/changed/deprecated/removed/fixed/security. Keep a changelog.

## API documentation

**OpenAPI / Swagger:** machine-readable contract. Generate client SDKs, server stubs, docs.

**Interactive docs:** Swagger UI, Redoc, Scalar, Stoplight. Try-it-out, auth, examples.

**Essential elements:**
- Authentication (API key, OAuth, JWT).
- Base URL, versioning.
- Endpoints: method, path, params, request/response schemas, examples.
- Error codes: codes, messages, remediation.
- Rate limits, pagination, versioning.
- SDKs: install, quickstart, common operations.

**Tools:** Stoplight, Redocly, Scalar, Mintlify, ReadMe, Postman, SwaggerHub, Redoc.

## Docs-as-code

**Workflow:** write in Markdown/MDX → Git → CI (lint, link check, spell check, build) → preview deploy → merge → production deploy.

**Tools:** MkDocs, Docusaurus, VitePress, Astro Starlight, Nextra, GitBook, Notion (export), Hugo, Jekyll.

**CI checks:** markdownlint, vale (prose lint), linkcheck, spellcheck, broken anchor check, build verification.

**Versioning:** versioned docs (Git tags, branches). `latest` + versioned paths (`/v1/`, `/v2/`).

**Localization:** i18n (Crowdin, Lokalise, Transifex). Separate repos or branches per locale.

## Developer Experience (DX)

**DX = UX for developers.** Friction points: onboarding, auth, errors, debugging, upgrades.

**Onboarding:** 5-min quickstart, interactive sandbox, copy-paste examples, SDK install.

**Auth:** simple (API key), standard (OAuth 2.0/OIDC), granular scopes, short-lived tokens, refresh.

**Errors:** actionable (what, why, how to fix), error codes, correlation IDs, links to docs.

**Debugging:** request/response logging, replay, sandbox mode, mock server.

**SDKs:** idiomatic (language conventions), typed (TypeScript, Go, Rust), tested, versioned.

**Feedback loops:** in-docs feedback widget, GitHub Issues, Discord/Slack, NPS.

## Content strategy

**Audience analysis:** who (dev, PM, ops), skill level, goals, context.

**Information architecture:** logical grouping, consistent naming, searchable, scannable.

**Style guide:** voice (direct, concise, active), terminology glossary, formatting conventions (code, UI elements, placeholders).

**Accessibility:** alt text, heading hierarchy, color contrast, keyboard navigation, screen reader tested.

## Measuring docs quality

**Quantitative:** page views, time on page, search queries (zero-results), CTA conversion, API docs usage.

**Qualitative:** feedback widget (👍/👎 + comment), support ticket deflection, NPS, usability testing.

**KPIs:** time-to-first-success, docs-driven support reduction, onboarding completion rate.
