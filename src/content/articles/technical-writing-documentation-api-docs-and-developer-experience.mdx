<Lead>
Developers often treat documentation as the thing they write after the code is finished. Users experience it as <Mark>the thing that determines whether the code is usable</Mark>. A technically excellent library with unclear documentation has a higher real cost than a mediocre one with a good guide, because the user pays the difference in time and confusion.
</Lead>

**Direct answer:**

<KeyPoint>
Technical writing is the practice of helping a specific reader complete a specific task with the minimum of avoidable friction.
</KeyPoint>

The Write the Docs guide is explicitly "a living, breathing guide" that "gathers the collective wisdom" of the documentation community, and GitHub's README documentation defines what a repository README should convey. The boundary: documentation cannot compensate for a broken product, and it decays unless someone owns its upkeep.

## Start with the reader's task

Four questions produce a useful document:

1. **Who is reading?** A newcomer, a returning user, and a contributor need different documents.
2. **What are they trying to do?** "Understand the system" is not a task; "make the first API call successfully" is.
3. **What do they already know?** Explaining HTTP to an experienced backend developer wastes their time; failing to explain it to a newcomer blocks them.
4. **How will they know they succeeded?** A doc that ends without a verifiable outcome leaves the reader unsure.

The Write the Docs guide organises its material around exactly this kind of practical division — getting started, approaches, markup, tools, and API documentation. Its framing as a "living" guide is itself a lesson: <Mark>documentation is maintained, not delivered</Mark>.

## The layers of a documentation set

A complete set usually has four layers, each with a distinct job:

**The README** answers "what is this and how do I start?" GitHub's documentation describes the README as the file that introduces a repository, which is why it is the first thing a visitor sees.

**The quickstart** gets a user to one successful result with the shortest possible path. It should not explain every option; it should produce a working outcome.

**The reference** documents the full surface — endpoints, parameters, return values, errors. It is searched, not read linearly, so precision and consistency matter more than narrative flow.

**The explanation** covers concepts, trade-offs, and why the system is designed as it is. This is the layer most often missing, and the one that lets a user solve a problem the docs did not anticipate.

<Trap>
Conflating these layers produces the familiar document that begins with a history of the project, continues through a configuration reference, and never tells the reader how to make the first call.
</Trap>

## A worked example of a README

The following structure is illustrative, not a quoted template.

Suppose a small Python library has a README with five sections. Test each against the reader's first five minutes:

1. **One-sentence description** — names the problem and the audience. A visitor should know in five seconds whether to keep reading.
2. **Install command** — copy-pasteable, with the supported Python version stated. An unpinned or unversioned instruction fails on a different environment.
3. **Ten-line example** — produces a visible result. If the example needs credentials, a test account or a clearly labelled mock must be provided.
4. **Links** — to the quickstart, reference, and explanation, so the reader can choose the next step.
5. **Constraints** — known limitations and the licence. Hiding a limitation in a later page costs the reader trust when they discover it after integrating.

Now audit for friction:

- If a new user must edit three files before the example runs, the example is not a quickstart.
- If the install command works only on one operating system, the environment assumption must be stated.
- If the README says "see the docs" without a path, the reader's task has been abandoned.

The measure is <Mark>time-to-first-success</Mark>. A ten-line example that runs is worth more than three pages of architecture description, because it converts a reader into a user who now has a reason to learn more.

## Style is a tool for reducing effort

The Microsoft Writing Style Guide is referenced here as a mature example of an institutional style guide. Its value is not a set of arbitrary rules; it is the principle behind them — consistent terms, short sentences, and a clear distinction between tasks and concepts.

Three rules transfer widely:

- **Use the same word for the same thing.** Switching between "workspace", "project", and "environment" for one concept forces the reader to maintain a mental dictionary.
- **Put the action first.** "Click Save to store the configuration" is easier to follow than a paragraph that arrives at the action at the end.
- **State the precondition before the step.** An instruction that assumes a running service fails silently for a reader who does not have one.

Style guides are not substitutes for thinking about the reader. They encode past decisions so that a team does not re-litigate them on every page.

## What documentation cannot do

Three limits matter.

**It goes stale faster than code changes.** A refactor that renames a parameter invalidates every example that uses it. Without a docs check in CI or a named owner, the reference drifts away from the implementation, and stale documentation is worse than none because it is confidently wrong.

**It cannot fix a confusing interface.** If a function's behaviour is surprising, adding a paragraph explaining the surprise documents a design problem. The better fix is often in the API.

**More is not always better.** A long tutorial can bury the answer a returning user needs. Separate the layers rather than extending one document indefinitely.

Documentation supplies the context the code cannot carry.

<PullQuote>
The counterargument — that good code is self-documenting — is true only for a reader with the context to read it.
</PullQuote>

## A decision test

1. **Name the reader and their task** before writing a line.
2. **Separate README, quickstart, reference, and explanation** so each has one job.
3. **Test the quickstart** in a clean environment with a new user if possible.
4. **State versions and assumptions** in every install instruction.
5. **Use consistent terms** and define them at first use.
6. **End with a verifiable outcome** so the reader knows they succeeded.
7. **Assign an owner** and a review trigger tied to code changes.
