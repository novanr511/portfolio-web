"AI agent" has become a vendor label for everything from a chatbot to a cron job. The label is not the distinction. The distinction is who decides the sequence of actions.

**Direct answer:** Traditional automation follows a fixed, human-written path from trigger to action. An AI agent uses a model to decide which actions to take, in what order, and whether to repeat—meaning the execution path is not fully determined in advance. The difference is not intelligence; it is delegation of control: the programmer decides in automation, the model decides at runtime in an agent.

## Traditional automation: the path is written in advance

A traditional automated system is a directed graph built by a programmer. Trigger → condition → action → next condition → action. Every branch is enumerated. Every error case is (ideally) handled explicitly. The system does what it was told to do, no more and no less.

Examples: a CI pipeline that runs tests on push, a marketing email sequence that sends after a delay, a thermostat that turns on heating below a set temperature. The logic is visible in the code or configuration. You can read it and predict the output for a given input.

This predictability is the strength and the limit. Traditional automation excels at well-defined, repetitive tasks where the correct response does not change with context. It breaks when the world presents a situation the programmer did not enumerate.

## AI agents: the path is decided at runtime

An AI agent wraps a model inside a loop. The model receives a goal, observes the environment, chooses an action, observes the result, and chooses again—possibly many times—until the goal is met or a stop condition fires. The sequence of actions is not written by a human; it emerges from the model's outputs.

Examples: a coding assistant that reads a repository, plans a fix, edits files, runs tests, and iterates until tests pass; a customer-support agent that reads a ticket, queries a database, drafts a reply, and sends it. The path depends on the model's interpretation of the situation, not on a pre-written decision tree.

The consequence: the same input can produce different paths across runs. The agent may skip a step, repeat one, or take one the programmer never imagined. That flexibility is also the risk.

## The distinction that matters

| | Traditional automation | AI agent |
|---|---|---|
| Who decides the next action | The programmer, in code | The model, at runtime |
| Is the path fixed per input? | Yes | Generally no |
| Can you read the full logic? | Yes, in the source | Partially; model internals are opaque |
| What breaks? | Unhandled cases | Unexpected model behavior, drift, cost |
| How do you test? | Unit tests, expected outputs | Evaluations, traces, guardrails |

The table describes ideal types. Real systems often blend both: an agent that calls deterministic tools (automation) inside a model-driven loop (agent), or an automation script that calls a model for one step. The question to ask of any system labeled "agent" is: *which parts are fixed, and which parts does the model decide?*

## What changes when control shifts

When a model decides the sequence, three engineering problems replace or amplify the old ones:

**1. Non-determinism.** You cannot write a unit test that asserts "given input X, the system always produces output Y," because the model may choose a different path. You test distributions instead: across 100 runs, does the agent reach the goal within an acceptable cost and error rate?

**2. Tool misuse.** An agent with access to tools can call them in the wrong order, with wrong arguments, or too many times. A delete tool called repeatedly is not a bug in the tool; it is a consequence of the model deciding to call it. Guardrails (approval steps, rate limits, read-only modes) become part of the system design, not afterthoughts.

**3. Cost and latency.** Each model call costs money and time. An agent that loops ten times to solve a problem a script solves in one request is more expensive, not more capable. The comparison should be outcome per unit cost, not outcome alone.

## When to use which

Choose traditional automation when the task is well-defined, the correct response is stable, and predictability matters more than flexibility. Choose an AI agent when the task is ill-defined, context varies, and you are willing to trade determinism for the ability to handle novel situations.

Most production systems should use both: automation for the reliable backbone, agents for the variable edges. A system that routes support tickets by keyword (automation) and drafts responses with a model (agent) gets the benefits of each without the risks of either.

## The honest boundary

An agent is not "automation that thinks." It is automation with a model in the control loop. That model can be wrong, can be inconsistent, and can be expensive. Labeling a fixed script an "agent" does not change its behavior; labeling an agent a "script" hides its risks. The engineering question is always the same: who decides, and what happens when they decide wrong?
