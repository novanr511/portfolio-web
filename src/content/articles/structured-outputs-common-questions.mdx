## The mechanism

The first point is what a schema enforces. The structured-output guide describes constraining generation to a format, which means the result can be parsed. It does not mean <Mark>the values are true, complete, or appropriate</Mark>, and the difference matters when the output drives a decision.

<Figure src="/images/articles/inline/structured-outputs-common-questions-1.png" alt="A four-step flow: define the consumer, write the schema, validate values against the source, then evaluate on real cases." caption="Conceptual: valid JSON is evidence about format, not correctness." />

The second point is schema design. The use-case guides describe models in production, where the output is consumed by another system. A schema that is too loose produces values that need interpretation, while one that is too strict omits uncertainty, which is a design decision rather than a technical detail.

The third point is validation. A field that must be an integer can still contain the wrong integer, and a required field can be filled with a guess. Checking the output against the task, with a sample of real cases, is the step that turns <Mark>a format into a reliable interface</Mark>.

The sequence is: define the consumer, write the schema, add validation, then evaluate on real cases. The choices are local, so the conclusions are `inferred`; the mechanism is `source-reported`.

## A worked example

*Illustrative.* A system extracts invoice fields into a structured record.

Three checks decide. First, does the schema match what the consuming system needs, including missing values? Second, are the values checked against the source document, not only against the types? Third, what happens when the model is uncertain, and does the output represent that uncertainty?

The outcome is an interface with a validation rule. The scenario is hypothetical; the method is the contribution.

## Why valid JSON can be wrong

A format check passes when the shape is correct, which is independent of whether the content is right.

<KeyPoint>
Treating a parseable response as a correct one is the error this article exists to correct, and the remedy is a value check against the source.
</KeyPoint>

A further consideration is how uncertainty is represented.

<Trap>
A schema with no field for "unknown" forces the model to guess, and a guess that looks like a value is harder to catch than an explicit gap.
</Trap>

Allowing a missing value is a design choice that preserves honesty.

The schema also has to evolve with the consumer. A new field added downstream can break an old parser, and an old field that nobody reads still costs tokens. Reviewing the schema when the consumer changes is part of maintaining the interface, not an optional cleanup.

The third limitation is that a schema cannot make a model understand the task. A model that misreads the input will produce a well-formed wrong answer, and validation against the source is the only way to detect it. The structure helps the system, not the reasoning.

A schema that cannot express uncertainty forces a guess, and a guess looks like a value.

The consumer of the output should be defined before the schema, since a field nobody reads still costs tokens.

<PullQuote>
A parseable response is evidence about format, not about whether the model understood the input.
</PullQuote>

The schema should be reviewed when the consuming system changes, since an old field can become an error.

Validation against the source is the only way to catch a well-formed wrong value.

A format check is not a correctness check, and the two belong in separate tests.

A required field with no way to express uncertainty will be filled with a guess.

## A decision test

1. Define what consumes the output.
2. Write a schema that represents uncertainty.
3. Validate values against the source.
4. Check on real cases.
5. Review the schema when the consumer changes.
6. Record the design and recheck date.

## A counterargument

The format-versus-truth distinction is sound, but a critic would note how much of the argument rests on its own synthesis. The evidence-status table marks 'validate values beyond types' as inferred, and the worked example is explicitly hypothetical, so both illustrate a rule the sources do not state. The OpenAI guide documents that constrained decoding yields parseable output, and the Anthropic guides describe production tasks; neither establishes that validation against the source is the only way to catch a wrong value, which is the article's own conclusion. The strict-versus-loose schema trade-off is conceded to be a local design decision. The decision test is a useful heuristic, not a documented property of structured outputs, and readers should not mistake the former for the latter.
