When a page needs several resources, the order and pacing of their responses can affect when useful content becomes available. HTTP has a standard way to communicate priority preferences, but the signal is not a command that forces a server to send one response first. RFC 9218 defines an extensible prioritization scheme; its values are inputs that clients, servers, and intermediaries may use in scheduling decisions.

**Direct answer:** RFC 9218 defines the `Priority` HTTP field and protocol-specific `PRIORITY_UPDATE` frames for expressing response-priority information. Its initial parameters include `u` (urgency, 0 through 7, with lower numbers indicating higher precedence) and `i` (whether a response can be processed incrementally). A server may consider these signals alongside other information, but a client cannot depend on a particular transmission order or performance result. The effect must be measured on the actual delivery path.

## Why response prioritization exists

HTTP/2 and HTTP/3 can carry concurrent responses on a connection. When several responses compete for limited bandwidth or server resources, a scheduler has to decide how to allocate transmission opportunities. A stylesheet that blocks rendering may matter earlier to a browser than an image that can appear later; a resource that can be consumed in chunks may benefit from incremental delivery.

The server often has information about its own resources and workload, while the client has information about what it needs and can process. Priority signaling provides a way to communicate those preferences. RFC 9218 explicitly treats priority parameters as suggestions and notes that servers can combine them with other inputs or ignore them. There is no universal scheduling algorithm mandated by the RFC.

## What `u` and `i` mean

RFC 9218 defines two initial parameters:

- **Urgency (`u`):** An integer from 0 to 7. Lower values mean higher precedence; the default is 3. It communicates relative urgency, not an absolute deadline or guaranteed time slot.
- **Incremental (`i`):** A Boolean indicating whether the client can make meaningful use of a response as chunks arrive. Its default is false. This describes a processing preference, not a promise that the server will stream or that every partial chunk is useful.

A request can express these parameters in the `Priority` field. For example, the field value can be:

```http
Priority: u=0
```

This tells the receiver that the client views the response as high urgency. It does not make the request more important to the application in an authorization or business-policy sense, and it does not establish that the server accepted or acted on the preference.

## Header field and update frames

The `Priority` field can be used across HTTP versions as an end-to-end signal. RFC 9218 also defines `PRIORITY_UPDATE` frames for HTTP/2 and HTTP/3, allowing a client to revise the priority after sending a request. These frames are scoped to a protocol hop, unlike the end-to-end field.

That distinction matters when intermediaries are involved. A proxy or CDN may interpret the client’s signal, alter scheduling for its own connections, or forward priority information to a backend. A signal observed at the browser-facing edge does not prove that every downstream server received the same value or applied the same policy.

## Why a priority value is not a performance guarantee

The signal is only one input to scheduling. The server may be constrained by CPU, storage, congestion, application dependencies, backend latency, or other requests. The resource may be cached, the connection may not have competing responses, or a proxy may transform the request path. Under those circumstances, changing a priority value may have no measurable effect.

RFC 9218 also describes fairness trade-offs. Strictly serving every high-urgency response first can delay lower-priority work for a long time; implementations may allocate some bandwidth to other requests to avoid starvation. The prioritization scheme therefore offers a vocabulary for preferences, not a universal guarantee that the “most important” resource always finishes first.

This is separate from [HTTP 103 Early Hints](/articles/http-103-early-hints-what-the-interim-response-can-do), which can tell a client about resources before the final response. Early Hints concerns when the client learns about a potential resource; priority signals concern how response delivery may be scheduled. One does not guarantee the other.

## How to test a priority change

Treat a priority adjustment as a hypothesis. Use a controlled comparison that changes the signal while keeping page content, server configuration, cache state, and test conditions as comparable as possible.

1. **Choose a specific contention case:** prioritization may be invisible when responses are not competing for constrained resources.
2. **Confirm the signal on the wire:** inspect the request field and, where relevant, protocol frames or intermediary logs.
3. **Verify server behavior:** determine whether the serving implementation supports and uses RFC 9218 signals; do not infer this from a browser setting alone.
4. **Measure response timing and user outcomes:** compare resource start/finish timing and the relevant page experience metric across repeated runs or representative field data.
5. **Check for trade-offs:** ensure the change did not starve other resources, increase completion times elsewhere, or affect other clients sharing an intermediary.
6. **Keep results scoped:** report the tested browser, protocol, edge, and server configuration. Do not generalize one test into a universal HTTP/2 or HTTP/3 result.
